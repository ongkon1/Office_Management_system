# BE-0911 Production Data Import Strategy

Status: **Complete — binding implementation contract for BE-0912**  
Defined: **2 November 2026**  
Applies to: the nine dataset families in
`docs/backend/phase-9/be-0910-source-data-inventory.md`

## 1. Purpose and boundary

This document defines how owner-supplied production data is mapped, validated,
deduplicated, rejected, dry-run, approved, committed, reconciled, and rolled
back. `BE-0912` must implement these rules without weakening them.

This strategy does not import data and does not approve any source file. A
source extract is eligible only when its `BE-0910` manifest identifies its
owner, steward, cut-off, row count, checksum, source key, sensitivity, and
approved secure location.

Development seed records are excluded. Imported or external data passes the
same domain, authorization, effective-date, audit, and financial-precision
rules as interactive data.

## 2. Batch model and invariants

One source file and manifest form one immutable **import batch**. A release may
contain multiple batches linked by one release identifier. Every batch must
record:

- batch and release identifiers;
- dataset type and mapping-contract version;
- source-system name, source file name, cut-off date, row count and SHA-256;
- accountable owner, steward, uploader and approving actors;
- sensitivity, dry-run timestamps, approval timestamps and commit timestamp;
- counts for received, normalized, accepted, unchanged, rejected and committed
  rows; and
- final state: `received`, `validating`, `dry_run_failed`, `ready_for_approval`,
  `approved`, `committing`, `committed`, `rolled_back`, or `superseded`.

Rules:

1. Source files are immutable after receipt. A corrected file is a new batch
   with a new checksum and supersedes, never overwrites, the previous batch.
2. Internal UUIDs are generated by the application. Owner files use stable
   natural/source keys and never choose database UUIDs.
3. A row records its source row number, source key, normalized fingerprint,
   outcome, target identifier when committed, and safe error codes.
4. Each dataset batch commits atomically. A release commits in dependency order
   and rolls back in reverse dependency order.
5. A commit must use the exact checksum, mapping version, target-schema version,
   and target-data snapshot validated by the approved dry run. Any change makes
   approval stale and forces a new dry run.
6. Application identities cannot run imports. A dedicated migration/import
   identity with only the permissions required by `BE-0912` performs the job.
7. Imports write append-only audit events and never bypass normal constraints.

## 3. Canonical source representation

The canonical exchange format is UTF-8 CSV with a header row. An owner may
supply Excel, but `BE-0912` must convert each approved worksheet to canonical
CSV without evaluating formulas, preserve the original file/checksum, and
record the converted checksum. JSON and SQL dumps are not directly executable;
they must first be transformed into the canonical contract and approved.

Canonical rules:

- headers are `snake_case`, trimmed, unique, and contract-versioned;
- dates are ISO `YYYY-MM-DD`; instants are ISO-8601 with an explicit offset;
- local business dates are interpreted in `Asia/Dhaka`; stored instants become
  UTC;
- durations are non-negative integer minutes;
- percentages are decimal strings with at most two fractional digits and map
  exactly to integer basis points (`100.00` → `10000`);
- money and rates are non-negative decimal strings plus uppercase ISO currency;
- booleans are exactly `true` or `false`;
- blank means absent only for fields explicitly declared nullable; whitespace,
  `N/A`, `0`, and `NULL` are not interchangeable with absent;
- enum values use the canonical lowercase values in this document; and
- formulas, macros, external workbook links, executable SQL, and embedded
  credentials are rejected.

Text is Unicode-normalized, outer whitespace is removed, line endings are
normalized, and identifiers/emails are compared using their domain-specific
normalized form. Display text retains its approved spelling.

## 4. Common mapping and validation pipeline

Every dataset follows the same pipeline:

1. **Manifest gate:** verify owner, declared row count, file size, format,
   mapping version, SHA-256, cut-off, sensitivity, and source-system name.
2. **Safe parsing:** reject malformed encoding, duplicate headers, unexpected
   worksheets, formulas/macros, oversized rows, and header-version mismatch.
3. **Normalization:** convert only the explicit representations in Section 3;
   never guess dates, statuses, currency, identities, or missing references.
4. **Row validation:** required fields, lengths, enums, numeric precision,
   date ranges, and conditional fields.
5. **Batch validation:** natural-key uniqueness, effective-date overlap,
   allocation and total checks, parent/child ordering, and duplicate analysis.
6. **Reference validation:** resolve codes against accepted parent batches and
   the authorized target snapshot. Names are never used as foreign keys.
7. **Domain validation:** execute the same business rules used by interactive
   services, including department scope, Government restrictions, task state,
   leave balances, money precision, and period overlap.
8. **Simulation and reconciliation:** calculate inserts, unchanged rows,
   conflicts, totals and protected aggregates without mutating target tables.
9. **Approval and commit:** bind approvals to the exact dry-run evidence, then
   commit atomically and produce post-commit reconciliation.

Unknown columns are errors by default. A mapping version may explicitly mark a
column as ignored, but the dry-run report must list it so owners know it was not
loaded.

## 5. Dataset mappings

### 5.1 Employees and account roles

| Canonical source | Target | Transformation / rule |
|---|---|---|
| `employee_code` | `employees.employee_code`, `users.employee_identifier` | Required stable key; trim; case-normalized uniqueness |
| `display_name`, `preferred_name` | employee/user names | Display name required; preferred name nullable |
| `work_email` | `users.email`, `email_normalized` | Valid address; normalized uniqueness; no account enumeration in reports |
| `job_title`, `hire_date`, `employment_type`, `office_location`, `normal_work_mode` | employee profile | Validate enums and ISO date |
| `standard_daily_active_minutes`, `standard_weekly_active_minutes` | employee policy defaults | Integer minutes; weekly value must be policy-consistent |
| `status` | user and employee status | Canonical `active` or `inactive`; locked is an authentication event, not an import status |
| `role_key`, `role_effective_from`, `role_effective_to` | `user_roles` | Current keys: `super_admin`, `team_lead`, `employee`, `hr_manager`, `management`; new `finance_manager` assignments rejected |

Passwords, hashes, sessions, lockouts, 2FA secrets and reset tokens have no
mapping. New accounts enter the approved credential-setup flow.

Validation includes unique employee code/email, valid role dates, no retired
role assignment, and no inactive employee with an active future assignment
unless explicitly accepted as a scheduled reactivation case.

Natural key: normalized `employee_code`.

### 5.2 Divisions

| Canonical source | Target | Transformation / rule |
|---|---|---|
| `division_key` | `divisions.division_key` | Required stable slug; never generated from a mutable name during import |
| `name`, `description` | division display fields | Name required and unique under current schema |
| `is_government` | `divisions.is_government` | Exact boolean; controls protected authorization scope |
| `is_active` | `divisions.is_active` | Exact boolean; referenced divisions are deactivated, not deleted |

Natural key: normalized `division_key`. A changed name with the same key is a
conflict requiring owner-approved update intent; a changed key is a new
division and never an implicit rename.

### 5.3 Departments, assignments and department leads

This family contains three ordered sheets/files.

**Departments:** `division_key`, `department_code`, `department_name`,
`description`, `is_active` map to the division-owned department catalogue.
Name and code are normalized for uniqueness inside their division.

**Assignments:** `employee_code`, `division_key`, `department_code`,
`effective_from`, `effective_to`, `allocation_percent`,
`expected_weekly_minutes`, `is_primary`, `role_in_division`, `is_temporary`,
and `is_active` map to `employee_division_assignments`.

**Leads:** `division_key`, `department_code`, `lead_employee_code`,
`effective_from`, `effective_to`, and `reason` map to
`department_lead_assignments`.

Validation includes:

- employee, division and department must exist and be active for the effective
  start date;
- department must belong to the same division as the assignment;
- active new placements require a department;
- allocation maps exactly to 0–10,000 basis points; concurrent totals above
  100 percent are owner-review errors, not silently rescaled values;
- one effective primary assignment per employee;
- temporary assignments require an end date;
- effective ranges may not invert or overlap for the same natural key;
- a lead must be an eligible active employee in that division; and
- one effective lead per department, while one employee may lead multiple
  departments.

Natural keys: division + department code; employee + division + effective-from;
department + lead effective-from.

### 5.4 Holiday calendars and holidays

Calendar fields map from `calendar_key`, optional `division_key`, `name`,
`effective_from`, `effective_to`, and `is_active`. Holiday fields map from
`calendar_key`, `holiday_date`, `name`, `portion`, and `is_active`.

Allowed portions are `full_day`, `first_half`, and `second_half`. The holiday
date must fall inside the calendar's effective range. A calendar/date pair is
unique. Friday/Saturday weekly holidays remain policy configuration and are not
expanded into rows unless the owner explicitly supplied and approved them.

Natural keys: calendar key; calendar key + holiday date.

### 5.5 Leave types and opening balances

Leave types map from `leave_type_key`, `name`, `is_paid`,
`requires_attachment`, and `is_active`. Balances map from `employee_code`,
`leave_type_key`, `year`, `entitled_minutes`, `used_minutes`,
`reserved_minutes`, `unit_minutes`, and `balance_cutoff_date`.

All amounts are integer minutes. Values must be non-negative, unit minutes must
be positive, and used + reserved may not exceed entitlement. The cut-off must
match the batch manifest. Owner reconciliation is by leave type and grand
total for entitled, used, reserved and remaining minutes.

Natural keys: leave-type key; employee + leave-type key + year.

### 5.6 Projects and memberships

| Canonical source | Target / rule |
|---|---|
| `project_code`, `division_key`, `name` | Required project identity and parent division |
| `status` | `planned`, `active`, `on_hold`, `completed`, or `closed` |
| `manager_employee_code` | Resolve to an employee effectively assigned to the project division |
| `start_date`, `end_date`, `priority`, `estimated_minutes` | Validate dates, enum, and integer duration |
| `description`, `completion_percent`, `accepts_time_entries`, `is_active` | Completion is 0–100; closed/inactive combinations require explicit owner intent |
| `budget_amount`, `currency` | Both present or both absent; fixed decimal string; protected |
| `client_name` | Preserve historical label only; do not create a first-class Client implicitly |

Membership fields are `project_code`, `employee_code`, `role_in_project`,
`allocation_percent`, `effective_from`, `effective_to`, and `is_active`.
Members/managers must have an effective division assignment. Government scope
is derived from the division and cannot be overridden by a source column.

Natural keys: project code; project + employee + effective-from.

### 5.7 Tasks and memberships

Task fields are `source_task_key`, `project_code`, optional
`parent_source_task_key`, `title`, `description`, `creator_employee_code`,
`creator_role`, optional `assignee_employee_code`, `status`, `review_state`,
optional reviewer/decision facts, `priority`, `estimated_minutes`, `start_date`,
`due_date`, optional `completed_at`, and `is_active`.

Mappings and rules:

- project determines division; a conflicting supplied division is rejected;
- stored status is only `pending`, `in_progress`, or `completed`;
- `overdue` and `upcoming` are rejected as stored statuses;
- Team Lead self-created tasks are self-assigned with `review_state =
  not_required`;
- an Employee-created task cannot be imported as `not_required` and cannot be
  made approved without valid reviewer/decision history;
- Completed requires a completion instant; non-Completed must not fabricate
  one;
- parent must belong to the same project and cannot create a cycle;
- assignee/supporting members must be eligible for the division/project; and
- task import creates no time, transitions, or actual hours.

Membership rows use `source_task_key` + `employee_code`. Natural task identity
is source-system name + source task key; the import crosswalk retains the
generated application UUID for idempotent reruns.

### 5.8 Effective cost rates

Fields are `source_rate_key`, optional `employee_code`, optional
`division_key`, optional `project_code`, `rate_amount`, `currency`, `rate_unit`,
`effective_from`, `effective_to`, and `is_active`.

At least one scope identifier is required. References must be mutually
consistent, rate amount must be a fixed-precision non-negative decimal string,
currency must be uppercase ISO (BDT unless an authorized owner approves
otherwise), and unit must be `hour`, `day`, or `month`. Effective ranges may not
overlap at the same precedence/scope. The owner-approved precedence rule is
mandatory before a batch can pass dry run.

Natural key: source-system name + source rate key. Rejection reports redact the
rate amount unless viewed by an actor with `finance.cost.view`.

### 5.9 Opening timesheet and payroll periods

Timesheet fields are `timesheet_period_label`, `start_date`, `end_date`,
`timesheet_status`, and `policy_version`. Payroll fields are
`payroll_period_label`, the same boundaries, `payroll_status`, and the linked
timesheet label.

Only an owner-approved opening state may be imported. Verified, amended,
exported, or closed history requires a separate historical migration with its
supporting immutable records. Ranges may not overlap existing periods, the
policy must cover the full range, linked boundaries must agree, and all parent
data effective during the period must already be accepted.

Natural key: start date + end date for each period family.

## 6. Duplicate and existing-record policy

Duplicate behavior is deterministic and never last-write-wins:

| Condition | Outcome |
|---|---|
| Same natural key appears twice in one batch with identical normalized values | Keep one staged candidate, mark later rows `DUPLICATE_IDENTICAL`, count as unchanged/warning |
| Same natural key appears twice with different values | Reject every row for that key as `DUPLICATE_CONFLICT` |
| Crosswalk shows the same source key/checksum was already committed | Idempotent no-op; return the original target id |
| Natural key exists in target and normalized business values are identical | Mark `EXISTING_UNCHANGED`; do not update version/audit timestamps |
| Natural key exists but values differ | Reject as `EXISTING_CONFLICT` unless the mapping contract explicitly supports an owner-approved effective-dated supersession |
| Different natural key collides with a unique email/code/date range | Reject as `UNIQUE_CONFLICT`; never merge identities automatically |
| Parent row is rejected or missing | Reject dependent row as `DEPENDENCY_REJECTED` |

Imported history is not overwritten. Effective-dated corrections create a new
period or close/supersede an eligible period through the approved domain rule.
Referenced records are deactivated rather than deleted.

## 7. Rejection reporting

There are two failure levels:

- **Batch-fatal:** checksum/row-count mismatch, unsafe file, unsupported header
  version, unreadable encoding, missing manifest/owner, stale schema, or stale
  approved snapshot. No row is eligible for commit.
- **Row rejection:** a syntactically readable row fails mapping, reference,
  duplicate, authorization, or domain validation. The dataset cannot commit
  until the owner supplies a corrected batch or explicitly approves an allowed
  exclusion under the rules below.

Every rejection row contains batch id, dataset, safe source row number, source
key or its hash where sensitive, severity, stable error code, field, safe
message, corrective guidance, related source key, and rule version. It never
contains passwords, tokens, raw protected notes, full PII snapshots, or
unauthorized financial values.

Minimum error codes:

`MANIFEST_INVALID`, `CHECKSUM_MISMATCH`, `HEADER_UNSUPPORTED`,
`UNSAFE_CONTENT`, `REQUIRED`, `INVALID_FORMAT`, `INVALID_ENUM`,
`OUT_OF_RANGE`, `REFERENCE_NOT_FOUND`, `REFERENCE_INELIGIBLE`,
`DATE_OVERLAP`, `DUPLICATE_IDENTICAL`, `DUPLICATE_CONFLICT`,
`EXISTING_UNCHANGED`, `EXISTING_CONFLICT`, `UNIQUE_CONFLICT`,
`DEPENDENCY_REJECTED`, `PROTECTED_SCOPE_DENIED`, and `STALE_DRY_RUN`.

The summary gives received/accepted/unchanged/rejected totals and authorized
reconciliation aggregates. Counts and error timing are authorization-filtered
before presentation so protected or Government records cannot be inferred.

## 8. Dry-run procedure

A dry run is mandatory for every batch and mutates no production business
table.

1. Verify and quarantine the immutable source and manifest.
2. Parse and normalize into isolated staging owned by the batch.
3. Run all common and dataset-specific validation.
4. Resolve references against accepted parent batches and a recorded target
   snapshot/version.
5. Simulate the complete dataset transaction, then roll it back.
6. Produce duplicate, rejection, proposed-change and reconciliation reports.
7. Record the mapping version, schema migration version, source checksum,
   target snapshot fingerprint and dry-run evidence checksum.
8. Move to `ready_for_approval` only with zero batch-fatal errors and no
   unresolved row rejection.

An owner may approve an intentional exclusion only when the source record is
outside the agreed migration scope, the reason is recorded, and referential or
financial reconciliation remains exact. Validation failures cannot be waived
to force invalid data into target tables.

## 9. Reconciliation and approval

Required reconciliation by dataset:

| Dataset | Required owner totals |
|---|---|
| Employees | Rows by active/inactive and assignable role; unique code/email counts |
| Divisions | Active/inactive and Government/non-Government counts |
| Assignments | Rows by division/department; primary counts; allocation totals and overlap exceptions |
| Holidays | Rows by calendar/year/portion |
| Leave balances | Entitled, used, reserved and remaining minutes by leave type and grand total |
| Projects | Rows by division/status; membership counts; authorized exact budget totals |
| Tasks | Rows by project/status/review state; assigned/unassigned/member counts |
| Cost rates | Rows by scope/unit/currency/effective state; protected values only for authorized approvers |
| Opening periods | Exact labels, boundaries, statuses, policy version and linked-period count |

Approval requires:

1. the accountable dataset owner approves the normalized row/rejection totals;
2. HR approves employee, assignment, holiday, leave and opening-period facts;
3. the authorized financial owner approves cost-rate totals and protected
   reports;
4. division/project owners approve their project/task scope, including
   Government classifications;
5. a Super Administrator or designated release operator approves technical
   readiness, dependency order, target snapshot and rollback readiness; and
6. no actor approves a protected dataset they could not ordinarily access.

Approvals record actor, role/permission snapshot, time, reason, batch checksum,
dry-run evidence checksum, mapping version and expiry. A source, mapping,
schema, target snapshot, rejection, or reconciliation change invalidates every
earlier approval.

## 10. Commit and rollback strategy

### Commit

- Place the application in the release mode chosen by `BE-0914` so interactive
  writes cannot invalidate the approved snapshot.
- Recheck checksum, approvals, schema version, target fingerprint, dependency
  batch states and authorization.
- Commit one dataset batch in one transaction; create crosswalk and audit rows
  in the same transaction.
- Re-run reconciliation from committed target records and compare it with the
  approved dry-run totals before continuing to the next dependency.
- Stop the release on any mismatch. Never continue with a partially accepted
  dataset.

### Rollback before business use

If a committed batch has no dependent batch or later business reference, the
import operator may run its reviewed rollback plan inside a transaction. It
uses batch-owned target/crosswalk identifiers, revalidates that no foreign
reference or later version exists, and reverses the release in this order:

1. opening payroll/timesheet periods;
2. cost rates;
3. task memberships and tasks;
4. project memberships and projects;
5. leave balances/types and holidays/calendars;
6. department leads, assignments and departments;
7. roles/accounts/employees and divisions, only when still unreferenced.

The rollback itself is audited and reconciled. It never uses broad table
truncation, name-based deletion, disabled foreign keys, or an unbounded SQL
script.

### Recovery after business use

Once an imported row has business references, logged work, verification,
audit history, or a later version, physical rollback is prohibited. Recovery
uses the normal domain action: deactivate, effective-date a superseding row,
correct through an authorized workflow, amend/unlock a verified period with a
reason, or restore the pre-release database only under the `BE-0914` disaster
rollback decision. Historical records and audit evidence remain readable.

Before production commit, operations must hold a tested database backup and a
recorded restore point. Restore-versus-roll-forward triggers and responsible
owners are finalized in `BE-0914`; backup/restore proof remains a Phase 8/9
release gate.

## 11. BE-0912 implementation acceptance contract

The implementation task is not complete unless automated tests prove:

- manifest and checksum enforcement;
- exact normalization for dates, minutes, percentages and money;
- all dataset-specific references and domain rules above;
- identical reruns are no-ops and conflicting duplicates are rejected;
- rejection reports are stable, corrective and free of unauthorized values;
- dry runs make no target-table changes;
- stale approvals cannot commit;
- each batch is atomic and dependency failures stop the release;
- post-commit totals equal approved dry-run totals;
- safe rollback works only for batch-owned, unreferenced records; and
- audit/crosswalk evidence survives commit, failure and rollback.

No owner source data or application business record is changed by `BE-0911`.
